# my-pi-goal

[English](README.md) | 简体中文

[模型提示词说明](docs/prompts.md)：每次符合条件的请求只注入一份当前执行规则，并从日志重建最新目标状态；上下文压缩后也会重新生成。停滞诊断使用英语产品文案，引用的用户内容保留原文，完整诊断不再被截断。

插件界面、命令、工具提示和其他文档均使用英语；用户目标与证据保留原文。

面向 Pi 长期兼容使用的个人目标插件：先澄清复杂需求，再持续执行、保存证据、运行检查并独立验收。适用于复杂问题修复、科研分析和从需求搭建项目，也支持按顺序处理多个目标。

第一版已实现并通过离线行为测试与真实 Pi 宿主集成测试。尚未进行付费模型下连续 5–12 小时的长时试运行，不把离线测试结果当作长期稳定性或研究结果正确性的保证。

## 开始使用

在任意项目目录启动 Pi 后执行 `/reload`，即可使用已经登记到个人全局配置的插件。

临时用于其他项目：

```bash
cd /path/to/your-project
pi -e /absolute/path/to/my-pi-tools/goal/extensions/index.ts
```

需要个人全局安装时：

```bash
pi install /absolute/path/to/my-pi-tools/goal
```

安装后，在其他项目中也可以直接使用 `/goal`。如果当前 Pi 已经运行，执行 `/reload`。

第一版以本地源码路径登记到个人全局 Pi 配置，包保持 `private: true`，没有发布 npm 包。当前项目没有项目级 package 声明，避免同一个插件重复加载。

```text
/goal 修复导出功能遇到中文文件名时报错的问题，并验证现有格式兼容性
/goal
/goal approve
/goal panel expand
/goal add 为这次修改补充用户文档
/goal pause
/goal resume
```

`/goal <目标>` 会先让模型只读调查并提交规格。短小目标的初始规格可直接开始；较长、科研分析、项目搭建、迁移和发布类目标需先确认。自动分类是简单启发式；目标已经完整时可用 `/goal start <目标>` 显式快速启动。快速启动仍要求形成验收标准并经过独立验收。

也可以直接说：“用 goal 修复导出问题，持续工作直到验证通过。”模型可调用 `goal_create` 创建目标，再用 `goal_plan` 规划，无需你先输入创建命令。你要求继续时，模型可用 `goal_resume` 恢复已批准、阻塞已解决的目标；初始规格分类与独立验收要求和命令入口相同。

你可以直接在聊天中补充要求。插件持久化补充消息并向后续调用重新提供目标状态；模型可在执行、暂停或阻塞时用 `goal_plan` 提出修改。**对已批准规格的任何修改都需要你的 `/goal approve`，包括新增或重排任务。** 批准前保留原规格和证据；批准单纯的任务细化后，原任务 ID 与证据仍保留。完全相同的规格不产生修改。旧验收会被取消，过期结论不能完成新版本目标。详见 [模型生命周期工具](docs/model-goals.md)。

`goal_resume` 不会在同一轮执行中绕过用户暂停或运行保护：停止后至少需要一条新的用户消息；仍需满足规格已批准、预算足够等条件。仅询问状态不代表要求继续，模型应遵从当前指令。用户仍可用 `/goal resume` 显式恢复。

## 工作流程

1. **规格**：目标、类型、验收标准、任务、检查命令。
2. **执行**：模型正常使用 Pi 工具，并通过 `goal_progress` 记录证据、已尝试方法和下一步。
3. **续跑**：正常回复结束后，在 Pi 的 `agent_before_settle` 原生边界追加继续指令；优先处理排队的用户输入，取消和错误不自动复活。
4. **实际检查**：候选完成时在目标声明的验证环境中重跑全部已确认检查命令。
5. **独立验收**：新的模型上下文独立读取文件，对每条验收标准提交结论。执行器不能自行标记 complete。
6. **修复或完成**：验收失败返回具体问题，最多进行 3 轮自动修复；第 4 次连续拒绝后暂停。验收通过后才推进下一个已确认目标。

验收器必须实际读取文件或运行检查，并在后续模型轮次看到检查结果后，覆盖全部标准提交结论。未核实的标准必须标为失败。模型仍可能误判；逐条证据和确定性检查用于提高可审查性。

检查环境和独立验收使用同一份声明快照；`goal_environment` 只调整运行时能力，不修改验收标准、检查命令或已有证据。详见[验证环境](docs/verification-environment.md)。

## TUI

底部状态栏显示状态、轮次和只读标记。编辑器上方的目标卡片使用当前 Pi 主题，显示目标、任务进度条、证据覆盖、轮次/token 用量，以及下一步或等待确认的提示。宽屏还显示活动时间；未知用量会明确标注。

默认卡片六行（含边框）。`/goal panel` 切换显示/隐藏；`/goal panel expand` 展开任务与验收标准，`compact` 恢复紧凑视图，`show/hide` 明确显示或隐藏。隐藏卡片不暂停执行，状态栏仍保留。展开后每组最多三条，优先显示进行中的任务；较矮的终端会自动缩减。12–39 列使用无边框摘要，更窄时压缩为一行，长文本按终端列宽截断。

目标通过独立验收后，会保留 Verified 结果；当你发送下一条普通消息（终端或 RPC）且会话中没有未完成目标时，自动清空已结束的目标状态并隐藏面板和状态栏。这条消息仍正常处理，清理不会取消消息或触发额外模型轮次。若上一轮最终回复尚未结束，先完成用量记账再清理。历史日志和产物保留；扩展生成的输入、失败验收或仅跳过的目标不触发自动清理，未完成队列也不会被清除。发送普通消息前，仍可用 `/goal` 等命令查看结果。

目标、队列与面板偏好按 Pi session ID 隔离。同目录新建、fork 或 clone 的会话不会继承另一会话的目标或面板偏好；恢复原会话会恢复其记录。`/goal clear` 清空本会话的目标和队列，取消正在进行的工作，移除卡片和状态栏；历史日志保留。清空状态也会写入模型可见上下文；reload、压缩或切换聊天分支后仍重新注入当前状态。旧目标 ID 的调用只返回“不存在、未执行”的说明，不修改目标；清空不会触发额外模型轮次。只有新的用户请求才应创建新目标，创建后重新显示卡片。

任务完成与证据覆盖反映执行器记录；只有独立验收通过后才显示“验收通过”。待确认的修改提案会显示新的任务和标准，不复用上一版的完成进度。

## 命令

命令统一使用英语；旧中文命令别名已移除。

| 常用入口 | 行为 |
| --- | --- |
| `/goal` | 查看本会话目标、队列、ID、版本和待确认规格 |
| `/goal <目标>` | 自动调查和规划；简单目标可直接执行，复杂目标等待确认 |
| `/goal add <目标>` | 加入 FIFO 队列并请求规格提案；不自动批准 |
| `/goal approve [id]` | 按分段摘要审阅并确认规格 |
| `/goal pause` | 暂停当前目标和队列，保留进度 |
| `/goal resume [id]` | 自动取得写入权并恢复；原目标已结束时选择已确认队首 |
| `/goal clear` | 清空本会话目标和队列、取消工作并关闭面板；历史日志保留 |

补充或修改要求直接发消息，无需记忆 `plan/amend`。模型负责调查、拆解任务和提出规格变更；修改已批准规格仍需用户批准。写入权随操作自动获取，暂停/等待/完成后的空闲边界或会话关闭时自动释放，不需手动 `take-over/release`。若同一个会话仍在另一个 Pi 实例中执行，会拒绝同时写入；不同会话的目标日志互不占用。

`/goal help` 显示上述常用入口，`/goal help more` 查看偶尔使用的操作：

| 可选操作 | 行为 |
| --- | --- |
| `/goal panel [show\|hide\|compact\|expand]` | 显隐或调整面板，不影响执行 |
| `/goal skip [id]` | 按明确命令跳过目标，保留记录；无第二次确认，随后 resume |
| `/goal budget 100k`、`/goal budget none` | 设置或取消累计 token 上限；默认不限 |
| `/goal model provider/id`、`/goal model inherit` | 设置或恢复默认验收模型；默认继承当前模型 |
| `/goal permissions [autonomous\|confirm]` | 查看或调整执行策略，默认自主模式 |
| `/goal settings` | 查看配置和文件路径 |
| `/goal approve-exact <id> <revision>` | 无界面调用：批准已经审阅的精确版本 |

审批页按目标、类型、验收标准、任务、检查命令和执行权限分段显示。终端中可用 ↑/↓、PgUp/PgDn、Home/End 滚动审阅；Enter 确认，Esc 取消，也会遵循自定义确认/取消按键。长内容随窗口宽度换行，完整提案不截断。RPC 的标准确认框使用同一份可读摘要。

ID 支持唯一前缀。队首为未确认草稿时不会自动越过。旧 `status/list` 等同 `/goal`；`start`、`plan`、`amend`、`remove` 保留兼容但不在常用帮助中。`take-over/release` 已退役，只说明如何使用正常的 pause/resume/clear，不会误建名为这些命令的目标。

## 预算与自动暂停

**仅保留自动修复次数、无进展保护，以及默认不限的可选目标累计 token 预算。**

- 主执行器没有轮次或运行时长上限；轮次与活动时间仍统计显示。`/goal resume` 重置本次计数和连续失败/停滞计数，保留累计用量、历史时间和证据。
- 目标累计 token 默认不限，可用 `/goal budget 100k` 设置、`/goal budget none` 取消；包含可获得的执行、嵌套工具、验收及停滞诊断用量，包括重复输入和缓存读取，不重复加 reasoning token。
- 用量在响应结束后才明确，最后一次请求可能越过预算。token 上限不等同费用硬上限；未提供用量的响应标记为未知。
- 首次验收失败后最多自动修复重试 3 次，第 4 次连续失败后暂停。目标累计 token 不足不占用修复次数；调整 `/goal budget` 后 `/goal resume`，仍须实际检查和独立验收，不能削弱标准或重置证据。
- 主执行器 3 轮没有记录到新进展时，续跑指令要求改变策略；5 轮时由新上下文做一次独立停滞诊断，保存建议并暂停。复核不可用时也会暂停，不放宽验收标准。不同的成功工具结果、任务状态变化或新增证据会重置计数；重复相同工具结果不会。它是启发式，无法机械证明语义进展。
- 独立验收没有额外的轮次、token、总超时或单次输出上限；停滞诊断也不再设置额外的超时或输出额度。若明确设置了目标累计预算，则共同受其剩余额度约束；模型和宿主的原生限制仍然有效。
- 检查规格只需 `command`；CPU、内存、进程数、输出和创建/执行/清理期限由个人沙箱配置控制，默认检查期限 120 秒。取消时回收整台验证 VM。这些资源上限与目标整体预算、审计模型预算分开。
- 验收上下文完整保留目标、标准、任务和用户补充；任务证据和检查长输出按 ID 分页读取，标准证据只预载简短索引。文件分页等资源边界不是运行预算，仍保留。工具面板显示验收轮次与用量，日志保存诊断信息。

## 检查与权限

[Docker Sandboxes](docs/docker-sandboxes-setup.md) 已成为唯一验证后端，bubblewrap 已移除。每个检查与审计复跑使用全新 microVM、冻结源码和固定镜像；回收成功后才能完成目标。个人配置缺失时拒绝验证，不回退到宿主执行。该后端只隔离验证，主 Pi 的普通工具仍在宿主运行；实测范围见 [验收记录](docs/docker-sandboxes-acceptance.md)。

**默认使用自主执行模式（autonomous）。** 目标规格批准后，Goal 不再为工具调用额外弹出逐次确认。项目读写、联网调查、安装依赖、清理临时文件，以及在目标范围内使用已有外部工具，可以连续执行。提示词明确要求模型执行已授权工作，不为普通实现选择或“是否继续”反复等待。

启动前确认目标范围和验收标准；执行中修改已批准规格，包括增加或重排任务，都先记录提案并等待你的 approve。获批的任务细化保留原任务与证据；目标、标准或检查变化按新规格重新验证。缺少必要数据或凭据、无法解决的外部阻塞、达到预算及多次验收失败仍会暂停。

自主执行仅取消 Goal 自身的工具权限弹窗，**不会覆盖 Pi、其他扩展、操作系统或用户明确设定的限制**。它也不是发布、删除数据或执行范围外动作的概括授权：已批准目标中的外部动作无需重复问，相同操作若超出目标范围仍需用户授权。Goal 不尝试用命令关键字机械判断目标语义范围。

需要额外监督时使用 `/goal permissions confirm`。此模式保留原有路径和命令模式检查，对项目外写入、安装、联网、提交/发布、远程、危险命令及外部工具请求确认；相同工具参数的许可在当前目标内复用。无界面、拒绝或取消确认会暂停；Goal 不再为确认对话设置自动超时。它是协作式规则，不是任意脚本的强制沙箱。

执行策略在创建目标时保存，恢复与切换会话后仍生效；`/goal permissions` 显示实际模式。旧日志没有该字段时采用加载的配置，下一次批准或恢复会保存。要恢复已经因旧授权规则暂停的目标：

```text
/reload
/goal permissions autonomous
/goal resume
```

显式写过 `network: "ask"` 或 `install: "ask"` 的配置仍被尊重，即使 mode 为 autonomous。上面的切换命令将当前目标的这两个选项一并设为 allow。目标规格尚未批准时仍须先 `/goal approve`。

验收器只获得 `audit_read`、`audit_search`、`audit_list`、`audit_record`、`audit_check` 和提交结果的工具，没有通用 bash、写入工具或其他扩展。`audit_record` 读取本轮冻结的执行器证据或检查输出，不算独立产物检查。读取和搜索路径经过真实路径校验，禁止目录穿越和项目外符号链接。单文件文本大小上限 5 MB；二进制结果须由执行器提供可审查的文本/统计导出。

**检查需要 Docker Sandboxes 与固定 digest 的模板及检查镜像。** 真实项目、home 和宿主 socket 不挂载进 VM；检查在 VM 内的受限非 root 容器中运行。新目标默认使用临时可写副本，也可显式选择只读；所有写入均丢弃，启动或清理失败时停止验证。

使用 `goal_environment` 可选择 `readonly` / `ephemeral` 工作区，以及 `isolated`（离线）、`allowlist`（指定域名/端口）或 `open`（开放出站）网络模式；`deny` 拒绝列表优先。联网须经过 HTTP/HTTPS 代理，不能直连外网或访问宿主本地服务。新目标默认使用 `ephemeral`，已有目标保留原设置。`env: []` 表示不继承宿主环境；`variables` 可显式设置 `CI`、`TZ` 等非秘密值。使用 `/goal sandbox inputs` 可预览输入、排除项与拒绝原因；安全链接和绑定项目的夹具例外见 [边界设计](docs/sandbox-boundary.md)。环境调整不改变批准的规格；显式网络确认策略仍生效，授权绑定具体目标列表。旧 `host` 模式迁移为离线，需要重新选择联网权限。

### 存储与上下文效率

journal 以增量记录为主，每 25 个 revision 写入一次完整快照；文件未变化时复用已解析的内存快照，长目标无需在每次工具调用时重放并校验全部历史。外部写入或篡改仍会触发重新读取和哈希校验。执行上下文与默认 `goal_status` 只保留证据条数和预览，`goal_evidence` 按需分页读取原文；`STATUS.md` 仍是派生导出，历史 journal 保持只追加。

## 配置

按顺序合并个人 `${agentDir}/my-pi-goal.json` 和项目 `.pi/my-pi-goal.json`。默认不会创建文件。修改后 `/reload`；已存在目标保留累计 token 预算、修复/停滞保护和执行策略，可用 budget/permissions 命令修改预算/权限。只设置 `permissions.mode: "confirm"` 时联网和安装默认 ask；只设置 autonomous 时默认 allow。全局和项目中显式填写的 network/install 值优先于模式默认值。

```json
{
  "limits": {
    "maxTokens": null,
    "maxAuditFailures": 3,
    "noProgressWarn": 3,
    "noProgressPause": 5
  },
  "audit": {},
  "permissions": {
    "mode": "autonomous",
    "network": "allow",
    "install": "allow"
  }
}
```

升级兼容：旧配置中的 `limits.maxTurns`、`limits.maxSeconds`、`audit.maxTurns`、`audit.maxTokens`、`audit.timeoutSeconds` 全部忽略，旧目标和待确认规格中的 `checks[].timeoutSeconds` 也不再生效。读取日志时先校验完整原始哈希链，再规范化当前快照；下一次写入追加新快照，不改写历史记录或证据。旧 `/goal limits` 仅提示已移除，不设置上限。

固定验收模型时，在 audit 中同时添加 `provider`、`model`，以及可选 `thinking`（minimal/low/medium/high/xhigh/max）。默认继承当前模型及其思考等级。直接通过当前 Pi 的模型注册表调用，保留自定义 provider 和身份配置；不会复制凭据到项目日志。

## 科研目标

科研类型会加入四项标准：Markdown 分析报告、结果文件清单、数据/软件/引用来源记录、实际命令与可重复执行脚本。方法、结果解释和局限属于报告的一部分；不适用项必须说明，缺失数据不能靠生成内容代替。

插件管理验收记录；分析报告及来源清单由执行模型依据真实工作生成，再由验收器检查。具体统计方法和科学有效性仍需要适合任务的领域审查。

三个可复用规格示例位于 [examples/goal-specs.json](examples/goal-specs.json)。它们是合成验收场景，不代表已分析用户的科研数据。

## 状态、恢复和长时间运行

会话权威日志：`.pi/my-pi-goal/sessions/<SHA-256(sessionId)>/state.jsonl`。哈希键支持 SDK 自定义 session ID，并避免路径穿越。每条记录包含会话 ID、状态快照或增量补丁、递增版本、事件和校验链；写入时刷新到磁盘。同目录的 `STATUS.md` 提供可读记录；`goal_status` 返回当前日志的完整路径。项目配置仍是 `.pi/my-pi-goal.json`。

Pi 会话保存版本引用和面板偏好；`/tree` 暂停执行但不回滚本会话的目标日志。相同 session ID 的多个 Pi 实例仍受单写入者保护，自动获取时使用新 token，旧实例和旧租期的回调不能写入。自动释放等到本轮最终用量和队列推进处理结束；不会强抢仍在执行的实例。不同会话的任务仍操作相同工作区文件，需要自行协调代码修改，这里的隔离针对目标记录。

旧目录日志 `.pi/my-pi-goal/state.jsonl` 保留原样：带有旧插件引用的原会话首次恢复时，校验完整哈希链，只有与日志最后一个所有者 session ID 相同才自动复制到该会话目录。旧写入者必须已经退出或释放。新会话不接管旧目录目标；已有会话日志（包括 clear 后的空快照）不会再次导入。旧的多会话共享记录整体归最后一个所有者，不尝试猜测拆分历史。

进程退出、reload、会话替换或恢复后不会自动执行。使用 `/goal resume`，或在普通消息中要求继续，让模型调用 `goal_resume`；旧审计回调无法应用于新 generation。正常退出保存时钟，异常崩溃最多损失最后一个时钟检查点附近的活动时间，不把离线时长算作执行时间。

最后一行写入中断时，下一次写入先保存残片再恢复；中间记录损坏会拒绝写入。如果崩溃留下 `transaction.lock` 空目录，先确认其他 Pi 已停止，再移除该空目录并重新恢复。不要直接手改 `state.jsonl`。

持续 5–12 小时需要 Pi 进程存活，例如：

```bash
tmux new -s goal-work
cd /path/to/project
pi -e /absolute/path/to/my-pi-tools/goal/extensions/index.ts
```

第一版没有后台守护进程、自动模型切换或子代理编排。已有联网工具可以经授权使用；不额外提供搜索 API。SSH、浏览器、MCP 专用适配器、通知和并行代理留在后续范围。

## 开发与验证

```bash
npm ci --ignore-scripts --legacy-peer-deps
npm run dev:link-host
npm run check
npm test
npm run check:load
npm run check:format
```

Pi 核心包作为宿主提供的 peer dependencies 使用，不打包副本。`dev:link-host` 按当前 `pi --version` 查找托管安装；其他布局可使用 `npm run dev:link-host -- /path/to/pi/node_modules`。Pi 升级后再次执行该命令会刷新指向旧安装的符号链接；手工安装的依赖目录不会被覆盖。

## 核心协议形式化验证

核心控制协议已有 TLA+/TLC 有限状态模型检查：验收结果隔离、完成门禁、任务证据保全、队列 FIFO，以及日志事务的锁/所有权/版本链。验证包含正向安全性质、条件活性和必须被检出的故意变异；模型曾发现 `/goal add` 在跳过/完成后越过旧目标的问题，已修复并加入真实运行时回归。

```sh
npm run verify:setup
npm run check:compat
npm run verify:coverage
npm run verify:formal
npm run verify:evidence
```

现有十三个模型还覆盖权限确认竞态、用量与停滞、日志恢复、上下文清理、检查取消及续跑调度，并增加直接执行 TypeScript 的有限域穷举。见 [完整覆盖清单](verification/COVERAGE.md)、[验证方法与代码映射](verification/README.md)、[运行报告](verification/REPORT.md)。覆盖检查能发现未登记模块和模型，但不自动证明每个函数的所有行为；有限域穷举也不等于无界程序证明。模型边界、调度/工具返回假设和实现差距均在报告中说明；这不是对 LLM 正确性、文件系统断电行为或无限长执行的证明。形式化检查独立于 `npm test`，不会给 Goal 运行增加预算上限。

## 滚动双版本兼容策略

仅支持 Pi 的当前版本和紧邻的上一发行版本，目前为 **1.4.0 / 1.3.0**。使用公开 API，并通过精确 peer 范围与插件入口版本检查限定支持窗口；不再承诺长期向后兼容。已有目标日志的数据保护不因宿主支持窗口缩短而取消。

`npm run check:compat` 在两个隔离临时目录中执行双版本类型检查、完整测试和插件加载，不切换当前工作区链接，也不读取用户设置或真实会话。`check:load` 会真正检查插件及工具注册，并拒绝 CLI 与工作区依赖版本不一致；仅运行模型列表命令不代表插件加载成功。升级时更新支持窗口并运行 `npm run dev:link-host`，然后重跑检查，见 [支持策略和升级流程](docs/compatibility/support-window.md) 、[1.4.0 兼容记录](docs/compatibility/pi-1.4.0.md)、[1.3.0 兼容记录](docs/compatibility/pi-1.3.0.md) 与 [历史 1.2.0 兼容记录](docs/compatibility/pi-1.2.0.md)。1.1.0 的历史终端检查见 [兼容性记录](docs/compatibility/pi-1.1.0.md)。非 Linux 平台和真实模型长时间运行仍未验证。

测试使用离线模拟 provider 和临时工作区，不调用付费模型，不修改用户项目数据。涵盖独立验收、提前停下后的原生续跑、取消/修改要求的竞态、预算、重复结果、队列、日志损坏、恢复、分支、权限与真实只读命令执行。

真实模型恢复验证：[TeamAgents 验收预算阻塞与恢复](docs/incidents/2026-10-07-teamagents-audit.md)，记录相同会话下重跑检查、独立验收和日志完整性核验。这次短程验证不代表 5–12 小时稳定性已经通过。
